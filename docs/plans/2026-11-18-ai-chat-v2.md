# AI chat v2 — plan (2026-11-18)

Owner request: fix the guest AI chat on the public menu end to end — current model,
better behaviour, every ability switchable per restaurant, and the chat must adapt to
menu-only vs ordering restaurants. Branch `feat/chat-assistant-v2` (from dev d8799fb,
which already holds the bottom-sheet redesign). Opus orchestrates and reviews, Sonnet
implements; Surface in light/critical mode, so only targeted tests run locally and CI
does the full check.

## Ground rules

- All AI through OpenRouter (`src/lib/ai/openrouter.ts`); every call metered in
  `ai_usage_events`; demo tenants (Aurora, Bella Vista) never billed.
- What a restaurant can do comes from the tenant capabilities first, then its own chat
  switches. A switched-off ability is not registered as a tool and is absent from the
  prompt, not merely hidden.
- Menu-only restaurants (no guest ordering): no cart tools, no cart rules in the prompt,
  the widget ignores cart items, greeting/suggestions do not offer ordering. The chat
  never pays or checks out; the guest always uses the normal checkout.
- Both data paths change together: legacy Supabase route and the production owned path
  (`src/lib/chat-native.ts`, `src/lib/data/public-chat-turns*.ts`).

## Stage 1 — model, history, cart (done, 360cdf7)

- `src/lib/ai/chat-models.ts`: default `anthropic/claude-haiku-5.5`; panel list Haiku 5.5,
  GPT-5.6 Luna, Gemini 3.8 Flash, Sonnet 5.5; stored retired ids fall back at runtime.
- `GET /api/public/chat/[slug]/history`: the widget shows past turns after a reload.
- The cart no longer opens by itself when the assistant adds items.

## Stage 2 — switches and new abilities (in progress)

- `chat_addon_settings`: `ordering_help_enabled`, `staff_call_enabled`,
  `suggestions_enabled` (NOT NULL DEFAULT true), migration
  `20261118110000_chat_feature_switches.sql` in `supabase/migrations/` and
  `docs/owned-schema/`.
- Panel toggles, disabled with a hint when the plan lacks guest ordering / waiter calls.
- `updateCartItem` tool (change quantity, 0 removes) using cart line ids sent by the
  widget; swap = remove + add.
- `callStaff` tool, only from a table link with the waiter-call capability; executed
  server-side with the existing waiter-call logic and its limits.
- History responses `Cache-Control: no-store`.

## Stage 3 — streamed replies

- `streamText` in both paths; the widget renders text as it arrives, then the final
  event carries cart changes, staff call and remaining messages.
- Persist the user and assistant turns when the stream ends.
- Metering: read the cost from the final usage chunk of the OpenRouter stream (the
  current `meteredFetch` only parses JSON bodies). Key-rejection fallback to the
  platform key must still work before the first byte. Voice notes keep the same path.

## Stage 2b — shared-tablet mode (done)

- `history_enabled` (default on) in the same migration. Off: the widget stores
  nothing, close/reload/5 min idle start from zero, the session route always opens a
  new conversation, the history route returns an empty list. The restaurant's inbox
  keeps conversations either way.
- Owned reads probe `information_schema` for the four switch columns
  (`src/lib/data/chat-switch-columns.ts`); a missing column means "on", and an admin
  save of a missing column answers 409, so the minutes between deploy and the schema
  step break nothing.

## Stage 2c — global and per-restaurant model (done)

- `platform_ai_settings.chat_model` (superadmin AI settings) is the global default;
  `chat_addon_settings.openrouter_model` becomes nullable (null = follow the global),
  set per restaurant on the superadmin tenant AI card. Resolution: restaurant model if
  offered, else global if offered, else `DEFAULT_CHAT_MODEL`.
- The restaurant only sees the model in use (platform-managed, like the client key).
- The migration sets retired per-restaurant ids (gpt-4o-mini) to NULL so they follow
  the global default.

## Stage 4 — verification and release

1. Review each stage's diff; eslint and targeted vitest locally.
2. Merge into dev; full CI (unit, SQL, browser) is the first type-check and e2e run.
3. Release needs the owner's OK. The Owned schema workflow only applies on a main SHA
   whose CI (including the deploy) succeeded, so the code always lands first; the
   probes keep everything working until then. Order: dev → main, wait for CI/deploy,
   dispatch `Owned schema` apply with that SHA, read back. `zera o git` does not run
   the schema step: dispatch it by hand. Also apply the migration to the dev Supabase.
4. Production checks: `curl -N` a chat turn on Aurora and see deltas arrive over time;
   read one streamed `chat` row in `ai_usage_events` (read-only): `cost_usd > 0`,
   `billable = false` for the demo. Cost 0 means streamed calls go unbilled: turn
   streaming off until fixed.
4. Check on a real phone: sheet + keyboard, streaming, history, menu-only demo
   (Bella Vista) vs ordering demo (Aurora).
5. Journal entry and Current State update.

## Not in this plan (later, each switchable when built)

- Phone verification (SMS code) for the chat gate.
- Owner-written welcome, tone and extra info (daily specials).
- Compact menu context for very large menus.
- Human handoff / takeover from the admin inbox; chat on grid and feed views.
- Merging the duplicated legacy and owned chat flows.
